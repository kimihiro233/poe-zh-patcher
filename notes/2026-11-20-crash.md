### 真正的元凶：回滚上限写死 64 MB

撤表之后又出现了一次**不一样的**症状——用户截到客户端自己的报错框：

```
File not found: Metadata/StatDescriptions/stat_descriptions.csd
```

补丁器自己的诊断也说「上次写入没有正常结束」：

```
20261120-192738：日志记录越界（偏移 58498047120，长度 78508111，原文长度 79769601101）（已写回 41 块）
建议顺序：① 用 Steam/WeGame「验证游戏完整性」→ ② 重新运行本程序。
```

查 `tools/shared/GgpkUndo.cs` 的回滚判断：

```csharp
if (off < 0 || cnt <= 0 || cnt > (64 << 20) || off > m.OrigLength - cnt) → 越界，拒绝
```

**ggpk 的索引是一整块写下去的（3.30 时期就有 78.5 MB）**，超过 64 MB 上限 ⇒
**索引一旦写坏，回滚永远拒绝那一块** ⇒ 客户端读不到索引里的东西 ⇒ 「File not found」/闪退，
而官方给的出路是「验证游戏完整性」＝重下 79 GB。

**修法**：上限提到 512 MB（真正的边界判断 `off > OrigLength - cnt` 已经在挡垃圾偏移了），
并加一条回归用例（`--undo-test` 的场景 H：写 70 MB 的一块，断电后必须逐字节退回去）✓。

修完立刻见效：`已把 ggpk 退回写入前的字节（1 份日志 / 43 块）`，
**不用再「验证游戏完整性」**（省下 79 GB 下载）✓，客户端当场恢复可启动 ✓。

### 这轮的教训

1. **回滚路径要有测试**。索引 78 MB 这种「大块」早就超出了 64 MB 的上限，
   但没有用例覆盖「块大于上限时的回滚」✗ → 一次索引写坏就再也退不回去 ✗。
2. **发布前要在真机上跑一遍「装完 → 启动 → 玩」**。v0.7.0 的自检全绿
   （24/24）、sha 逐字节一致、指纹与锁相同 ✓，但客户端照样崩 ✗ ——
   补丁器的自检证明的是「我们写进去的字节没写错」，不是「游戏能读」✗。
3. **发布包一旦有问题要能自己退回去**。今天客户端的 ggpk 索引就是被这次安装写坏的，
   幸好日志里存着原始字节；修好上限后一条命令就退回去了 ✓。

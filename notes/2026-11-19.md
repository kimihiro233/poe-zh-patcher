### 环境坑（这一轮踩到的，下次直接用）

- **DSH 的工作区沙箱会限制「工作区内的可执行文件」**：`tools/dumper/bin/Debug/net8.0/dumper.exe`
  一启动就 `UnauthorizedAccessException`（读游戏目录里的 Content.ggpk 被拒），
  但同一台机器上的 python / pwsh 读同一个文件没问题。
  解法：把 dumper 连同同目录 DLL 拷到工作区外再跑。
  为此给 `tools/gameinfo.py` 与 `tools/dat_text_diff.py` 加了 `POE_DUMPER` 环境变量。
- **低完整性级别（Low IL）连只读打开 ggpk 都不行**：LibGGPK3 用 `File.Open(..., ReadWrite)`
  打开 Content.ggpk，Low IL 下写入请求被强制完整性标签挡掉（报「拒绝访问」而不是「共享冲突」）。
  `danger-full-access` 的会话是 Medium IL，能读写。
- **`edit` 工具在 Windows 上把 LF 写成 CRLF**，而这个仓库两种都有：
  `README.md` / `tools/*.py` 在 git 里是 CRLF，`out/*.csv` 是 LF。
  改完必须按 `git show HEAD:<file>` 的行尾把工作区对齐，
  否则 `git diff` 会显示整个文件都变了（`.gitattributes` 是 `* -text`，git 不做归一化）。

### 顺带修掉的两个工具问题

- `check_fixes.py` 的 UI 侧只看 `out/pairs.csv`，而 `extract_pairs.detect_slots()`
  只认出 currencyitems 的第一列 → 指向第二列的修正稿一律被判「gone」。
  改为：查不到就回 `pairs/zh/<表>` 直接读那个槽位（真值在，只是没被抽出来）。
  修之前每轮都有 1 条假警（跟游戏版本无关）。
- `patch_sd.py` 的报告把「官方自己已经修好了」和「原文漂移」都报成
  `✗ 原文不符（可能已改/已漂移）`。实测有 16 条 `fix-placeholder` / `fix-typo`
  属于前者（官方早已把占位符和笔误补对），每轮构建都假报失败。
  新增判定：定位失败但目标块里「修正稿新文本用到的占位符已经齐全」→ 报
  `✓ 上游已修正（本条可退役）`，不算失败。这 16 条留在清单里（官方哪天回退还能救回来），
  但不再污染构建。

### 本轮发现并修掉的四个工具问题

**1（破坏性，必修）statdesc 扩展名从 `.txt` 变 `.csd`**
`patch_sd.py` 的 `path_in_ggpk` 是硬拼 `"metadata/statdescriptions/" + name`，`build_bundle.py`
跟着写进数据包。3.30 里这个路径不存在，补丁器 `--status` 直接报 45 个「缺失 0 B」、
状态「未知 45」——看起来像客户端坏了，其实是路径过期。
改成读 `game.lock.json` 里的真实路径（`sd_path_in_ggpk()`），锁里没有才退回旧拼法。
同时把 `DataTest` / `SdTest` 改成按**主名**匹配、不认扩展名，否则换版本就整批「基线文件缺失」。

**2（中）内容闸白名单没跟上新标签**
3.30 原版新增两个标签：`<goldname>`（55 次）和带参标签 `<gemlevel={0}>`（101 次）。
前者白名单缺项，后者连语法都不认（G2 只认 `<name>` 与 `<rgb()>`）。
结果 `build_bundle` 报 30 处 warn——**这不是译文有问题，是闸门自己过期**。
白名单加 `param` 段（只允许 `<name={n}>`，不放行任意参数，避免 `<script src=..>` 混进来）。
Py 与 C# 两侧同步改，fixtures 补两条（一条 accept、一条白名单外 reject），17/17。

**3（低）产物目录残留旧文件**
`out/patch-sd/` 里留着 10-30 的 `chest_stat_descriptions.txt`（3.29 时代，4188 行），
本次 manifest 里没有它。`content_gate --scan` 因此报 G3「行数 4188 / 基线 3656」假警报。
`build_bundle` 按 manifest 取文件，所以没污染数据包（已核对 116 个 sha）。已移到 `out/stale-3.29/`。
**待做**：`--write` 结束时列出「目录里有、本次没产出」的文件，别让人靠肉眼发现。

**4（低）README 数字漂移**
`doc_check` 正确报警 6 类：ggpk 大小、statdesc 份数、基准份数、对照行数、
白名单标签数、对抗样本数。已同步为新值，13/13 通过。
注意改 README 时踩了行尾坑：Python `read()` 默认把 CRLF 转成 LF，写回后整个文件 860 行全变 LF，
`git diff` 显示 1720 行。用二进制读写修回，最终改动 17 行。

### 9 条「需要重做」的真相：官方已自行修好

`check_fixes` 报 8 drift + 1 gone，`patch_sd` 报 22 组 miss。逐条核对后结论是**修正稿退役**，不是重做：

- `fix-mult` 那 6 条：英文 `Scarabs found in Area` → `[Thread|Threads] found in Area`
  （3.30 新机制），官方繁中已重译为「區域內可找到{0}%更多[Thread|綢帶]」，
  结构与我们 2021 年那版修正稿一致，只是名词换了。无需再改。
- `fix-placeholder` 那 16 条：3.30 官方繁中已经补回占位符
  （`機會石有{0}%機率改為掉落古變石`、`投射物有 {1}% 機率返回你`）。
  剩下的「缺」是英文单数形式本来就没有占位符（`Vaal Vessel contains an additional Vaal Temple Map`），中文写「1 張」是对的。
- `fix-category-ui` 3 条：纯行号迁移（clientstrings 7910→7903，currencyitems 1932→1958、1933→1959），
  已在 `out/fix-category-ui.csv` 里更新并注明「3.30 行号迁移」，原表留档 `out/fix-category-ui.3.29.csv`。

`patch_dat` 第一次跑就正确拒绝：「行 7910 槽位 8 现值与清单不符」+「未生成 manifest」——
不是产出半套。这正是设计里要的行为。

## 发布 v0.5.7 + 真写入客户端

按要求「以当前版本发布，打补丁」，问过一句版本号：v0.5.6 的 tag 已打在 3.29 那版上，
同一个号不能打两次，于是升 0.5.7。

发布前补了两道自检（都属于「清单还会不会说话算数」这一类）：

- `build_bundle` 原来只把清单里的 sha 抄进数据包，不核对磁盘上那几份文件是不是它。
  现在逐份重算：45 份 × 三套 flavor + 5 张 .dat，对不上就 `return 4` 拒绝打包。
- 内容闸报告 0 命中时也落盘。以前「有命中才写」，白名单补好后 `out/content-gate.md`
  还留着 30 处旧警报，谁看都会当成这一次的结论。

### 真机写入（官方独立端，79,769,601,101 B）

`--status` 先看：50/50 官方原文、基准为空、语系与国旗都未启用 —— 干净的 3.30。
随后 `--set=translated`（纯译文，日常游玩）：

- 目标 50，实际写 **18 个文件**（13 份 statdesc + 5 张 .dat），`重新打开后回读 18/18 通过`
- 逐字节日志 76 块 / 81.7 MB；国旗与语系两项一并写好（语言列表第二项已是「繁體中文」）

### 写入时暴露的第五个工具问题：例外表按扩展名匹配，3.30 整张失效

第一次写入报 `内容闸[warn]：159 行已过，1 处命中`：

```
G3 skill_stat_descriptions.csd:1924 占位符与原文不一致：缺 {0}
```

查下去是 `fix-placeholder#6`（`當觸發時使用此技能投擲 {0} 個陷阱` → `{1}`，
英文原文就是 `Throws up to {1} Traps`，官方繁中编号错位，我们改对了），
它本来在 `tools/pack/gate-exceptions.json` 里，**但例外表按文件名匹配，而文件名在
`skill_stat_descriptions.txt` / `.csd` 之间换过一次**：Python 侧喂进去的是 raw_sd 的扁平
`.txt` 名（碰巧对上），C# 侧喂的是容器里的路径（`.csd`），于是只在 exe 里失配。
同一类坑这已经是第三次（`patch_sd` 拼路径、`DataTest` 找基线、现在是例外表）。

修法是两边都归一成「不带扩展名的名字」（`sd_stem()` / `Stem()`），而不是改调用点 ——
下次再换扩展名也不会重犯。顺带补两条对抗样本：同一个改动用 `.csd` 名必须放行，
换个文件名必须仍然拦（19 条样本，Py 与 C# 各跑一遍，改之前这条会红）。

### 第二个问题（不是 bug，是文档在说谎）

装完再 `--plan`，报「需要改动 18 个」而不是 0。查 `fbc41e3`（v0.4.6）：
「反复打补丁会把客户端打成 Buffer Underflow —— 不再复用历史自建 bundle」。
所以每次运行都会把已打过的文件重新落进一条新 bundle，这是**故意的**，
代价是写 ~80 MB（快照轮转，磁盘不累积）。README 里那句「再跑一次 `--plan` 显示需要改动 0 个」
是 v0.4.6 之前测的，已经改了措辞，不再让人以为没装好。

另外把三处漂移的数字绑上来源：「161 处修正 / 160 处修正」在 README 与 `Program.cs` 里各写一份、
都没人核，实际是 159。现在 `docs/claims.json` 把 `N 处修正` 与 `修正过的 N 行` 都绑到
`out/patch-sd/manifest-sd.json` 的 `total_edits`，`unverified` 里那条挂了三个版本的欠账清空。

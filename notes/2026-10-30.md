## v0.4.9：旧版补丁器写的对照版，必须认得出并接管

用户一句话点到了根子上：**「旧版补丁器直接认不出不行，应该要能认出来并接管。
准确地说，所有译文和原文的对应版都要能认出来，除非译文和原文对应被破坏了。」**

### 问题

`Detect` 用整块 sha 认状态。v0.4.3 改过 `dual_body` 的排列方式（英文整段附末尾 →
逐组穿插），于是所有早先写过的对照版整块 sha 全变了 → 判「未知」→ 全量替换中止。
这台机器上 25 个文件正好是这个状态，`--set=dualall` 直接 `return 5`，一个字都不写。

### 判据的粒度错了

「内容一样，只是行的排列不同」不该算「不一样」。改判据：从整块降到**行**。

- 行池 = `O` ∪ `T` ∪ `D` ∪ `E` ∪ `Legacy` 所有行，去标记、去首尾空白；
- 每一格的块内行必须全部落在池里，且至少一行来自译文类；
- 全部落得进去 → 我们某版本的排列 → 接管（`Flavor.DualLegacy`），整块换成目标；
- 有一行落不进去 → 那不是我们写的 → 不接管。

这条判据的意义不只是「修好当前这一版」：它不认拼法、只认行，以后 `dual_body`
再改多少次，老客户端都还认得出来。

### 实测

- `--status`：`未知 25` → `旧版对照 25`，每条都报「N 格是原文+译文的排列（0 格仍是原文）」
- `--plan`：25/25 演算通过，0 失败（说明生成字节与 `ShaDualAll` 逐字节一致）
- 真写：47/47 回读通过，状态 `全量对照 42 / 已打补丁 5`，长度仍 `74,730,084,326 B`
- 再跑 `--plan`：需要改动 **0** 个 —— 幂等

### 顺手修的

`--on-modified=skip` 的提示写着「保持它们现在的样子、只翻能对上的」，但实际非 partial
下仍然中止。现在 `skip` 自己就放行（`tolerate = partial || policy == Skip`），
pool 统一按 `!skip.Contains(i)` 排除，不再需要用户猜「是不是还得再叠个 --partial」。

### 新增自检

`--legacy-test`：用数据包三态文本现场拼 11 种情况 —— 6 种排列都要认出（逐组穿插、
英文附末尾带缩进/不带缩进、英文在前、混着来、只有译文），5 种必须认不出（英文那行改一个字、
译文那行改一个字、混进别人的译文、整份都是原文、一格已翻一格未翻要认出）。全部通过。

## v0.5.0：基准 —— 让结果与「改过几次」无关

### 需求怎么一步步收敛的

一开始我提的是「补一份官方原文进数据包」，理由是 statdesc 没有内嵌原文字节，
`--on-modified=ours` 对它做不到。用户的追问把方向改了三遍：

1. 「直接从客户端读，备份在 bundle 中」—— 不要预先打包，运行时读。
2. 「更改前从 content 里读出来并备份」—— 澄清时机：写之前读，那时可能还是原文。
3. 「如果已经被修改的版本，或者被其它补丁修改过呢」—— 指出这个方案的前提（第一次改动之前）
   经常不成立。
4. 「不带，我们优先要保证的是游戏内容的完整性，而不是原文」—— 目标不是保原文。
5. 「在当前基础上做备份，有备份的情况下以备份为前提算，即使多次修改，也可以还原」
   —— 最终方案：**备份即基准，当算式输入**。

最后这条把问题彻底转过来了。之前一直在问「怎么拿到原文」，用户问的是「怎么保证不越打越歪」。
这两个问题的最优解不一样：前者要把 5.9 MB 塞进发布包，后者只要把「第一次见到的样子」当常量。

### 方案

```
基准 = 该文件在这个游戏版本下第一次被本程序看到的完整字节
每次写入 = 基准 + 目标 flavor → 产物
```

输入是常量，结果就是常量。改一次和改两百次算出来的是同一份字节，不存在累积。

关键设计：

- **建基准时尽量取原文**：当前是译文就从数据包还原，还原后 `sha == sha_original` 才作数。
- **只存一次**：已有基准绝不覆盖，否则常量变回变量。
- **按游戏版本分目录**：`client_version + patch_version`。换版本换目录，旧的不删也不读。
- **不参与备份轮转**：备份是后悔药，会轮转；基准是常量，删了算式就变了。
- **sha 对不上就拒绝使用**：宁可从当前重算，也不拿污染的常量去算。

### 真客户端上跑通的五步

```
建基准      47 份全部还原成原文（sha 校验通过才标 Original），52.8 MB
→ --set=translated   47/47 回读通过，产物 sha 与发布产物逐字节一致
→ --set=dualall      47/47 通过
→ --baseline --restore-baseline=statdescriptions
                     42 份整份回到官方原文，状态「官方原文 42 / 已打补丁 5」
→ --set=dualall      47/47 通过，状态精确回到「全量对照 42 / 已打补丁 5」
```

「47 份全部还原成原文」这一步是最有说服力的：从「中文 + 英文对照」精确逆推出官方原文，
逐份 sha 校验通过。说明原文一直在数据包里，只是以前没把它当常量用。

### 顺带修的两件事

1. **`BackupStore.Add` 静默吞异常**。`Program Files` 下没写权限时备份会悄悄失败，然后照样
   写游戏文件 —— 等于把「没退路就不写」破在自己家里。现在 `BackupStore.Create` 和
   `Txn.Begin` 建不出目录就返回 null，上层拒绝写入并说清原因。
2. **`--plan` 与实写不一致**。`inherited`（还挂在旧自建 bundle 上）只在 `!plan` 时算，
   于是演算说「需要改动 0 个」，真跑却写了 47 个。现在两边都算。
3. **JSON 全带 UTF-8 BOM**。`Encoding.UTF8` 在 .NET 里是带 BOM 的，写出来的 `index.json`
   用 Python 直接读会炸。换成 `UTF8Encoding(false)`。

### 单文件 exe 的约束（用户提的）

补丁器是自包含单文件，会被新版本覆盖、会把运行时解到 `%TEMP%`。所以备份**不能跟 exe 走**，
必须跟容器走：`<游戏目录>\.poe-zh\`。现有四类存储（txn / backup / baseline / ggpk）全部
基于 `containerPath`，没有一处用 `AppContext.BaseDirectory`。基准的键是游戏版本而不是
补丁器版本，所以补丁器升级多少次，基准都还是那一份。

### P1-5 采集包脱敏

新增 `tools/shared/Redact.cs`。规则顺序不能换：**先整行剔除，再替换路径** —— 反过来的话
`C:/Users/Administrator/…` 会先变成 `C:/Users/<user>/…`，一行里还带账号时整行本该消失的，
却留下一个看起来干净的壳。

四条规则：整行剔除（账号/会话/令牌/邮箱，保留行首时间戳 + `[REDACTED]`）、用户目录只换用户名、
其它盘符路径换 `<path>`（仅日志）、SteamID64 换 `<steamid>`。`report.json` 的 `container.path`
删掉换 `path_hint`（盘符 · 层数 · 文件名）。

两个实现细节值得记：

1. **`\b(account|…)\b` 会漏。** 日志写的是 `logged in as AccountName#1234`，`AccountName` 的
   `Account` 后面紧跟 `N`（词字符），词尾边界不成立 → 整行剔除不触发。去掉尾部 `\b` 才行。
   这条是自检断言 2 钉住的。
2. **自检的第一版把 `C:/Users/<用户名>/…` 写进了 README.txt**，被 `Audit()` 判成泄漏、拒绝打包。
   自检误报自己人 —— 这是正确行为（`(?!<user>)` 只认字面占位符），说明兜底是真的在跑。
   顺手把示例文案改成不含路径字面量的写法。

验收（真客户端 C:/Program Files (x86)\…\Content.ggpk，74.7 GB）：
历史包 `out/collect-20261028/client-log.txt` 有 **27 行**带 `C:/Users/Administrator/`；
新包同一个文件 15 行都是 `C:/Users/<user>/AppData/Local/…`，真用户名残留 0 行、SteamID 0 处，
zip 正常生成（6,389 B）。`--redact-test` 11/11。

`grep -c 'Users\'` 这个验收口径本身是错的 —— 它连 `C:/Users/<user>` 一起数。真正的判据是
`Audit()` 里的 `[A-Za-z]:\\Users\\(?!<user>)`，手检用 `grep -cE 'Users\\\\[^<]'`。

历史清理：`.gitignore` 改成 `out/collect-*/*` + 三条 `!` 否定，只保留 `ANALYSIS.md` /
`syntax-check.md` / `*-diff.csv` 这些分析结论（已核对 0 命中）。注意必须写 `out/collect-*/*`
而不是 `out/collect-*/`：父目录被整体忽略后，`!` 规则进不去。
`git rm -r --cached` 只摘掉 8 个脏文件（两个 client-log / report.txt / report.json / README.txt）。
**不重写历史**：泄的是路径不是凭据，`filter-repo` 对已公开仓库的代价大于收益。

## P1-6 内容闸（v0.5.2 待发）

威胁模型换了。以前防的是「客户端被游戏更新弄脏」，现在防的是**数据包被人换过**：
`bundle.gz` 是随 exe 分发的二进制，一旦被塞私货，客户端就成了任意文本的展示器。
所以闸不问「译文好不好」，只问一句：这一行能不能用「原文 + 译文」按 markup 的三分法推出来。

五组规则 G1 字符集 / G2 标记 / G3 结构 / G4 体量 / G5 可推导。三个接入点
（patch_sd 写清单前、build_bundle 打包前、dropper 写第一个字节前），少一个就有旁路。

### 三处「按提案做会把自己卡死」的地方

1. **G3 的参照物不能是原文。** 提案写「占位符集合 = 原文」，可是双语 flavor 会在中间
   插 `\n`，一比对就全是「多 \n」—— 首版扫 `out/patch-sd-dual-all` 命中 253,752 处。
   改成两级：有 `want`（运行时 bundle 说的目标）就**逐项相等**，没有 `want`（扫产物时
   手上只有官方原文）就退化成**子集**——原文的占位符一个都不许丢，多出来的放行。

2. **闸的作用域是「将要写进客户端的那一行」，不是整份文件。** 首版逐行扫整份，官方原文
   里那些 `{0]` 笔误、`1|#` 前缀全被算成违规。改成只查「与基线不同的行」，并且只查
   引号内的文本段（`text_span`），命中从 253,752 降到 4。

3. **那 4 处是真命中，不是误杀。** 全是 `fix-placeholder` 的编号错位修正：官方写
   `{1}`、实际参数是 `{0}`（游戏里渲染成空），我们改成正确的编号。这类「故意不同」
   必须有地方记，于是有了 `tools/pack/gate-exceptions.json`——按**完整文本**匹配，
   不按行号（换版本行号全变，文本不变），每条都要写原因。

### 数据闸拦不到的边界

`--scan` 只拿得到官方原文、拿不到 `want`，所以只能做子集检查；「`want` 自己把占位符
写错」交给 `check_placeholders.py`（它手上有 en/zh 两份原文）。这条边界要写清楚，
否则下个赛季有人会以为闸管了一切。

### 两侧实现

`tools/content_gate.py` 与 `tools/shared/ContentGate.cs` 同构，**共用一份**
`fixtures/gate/cases.json`（15 条：13 拒 + 2 收）。C# 侧 `--gate-test` 读同一份，
任何一侧单独改规则另一侧就红。策略表（白名单 / 例外）也随 exe 内嵌——玩家机器上没有
仓库目录树，读不到白名单会把每个命名标签都判成「不在白名单」→ 全量误杀。

试过把磁盘上的白名单清空再跑，C# 侧立刻 181 行里命中 4 处并拒绝写入（exit 7），
证明内嵌回落与 enforce 都是真的在跑。

### 灰度

`--gate=off|warn|enforce`，默认 warn。三套 flavor 全量扫过：

| 产物 | 文件 | 命中 |
|---|---|---|
| out/patch-sd | 14 | 0 |
| out/patch-sd-dual | 14 | 0 |
| out/patch-sd-dual-all | 42 | 0 |

真机（官方独立端）：`--set=dualall` → `内容闸[warn]：26635 行已过，0 命中`。
自检：`--gate-test` 15/15（C#）、`content_gate.py --test` 15/15（Py）、
`--redact-test` 11/11、`--data-test` 42/42、`--markup-test` 11/11、`--legacy-test`、
`--undo-test`、`--baseline-test`、`doc_check` 11/11（新增 3 条 gate 断言）。

### 一个坑

`config.Load` 原来只读磁盘。单文件 exe 的 `AppContext.BaseDirectory` 是 %TEMP% 解压目录，
玩家机器上根本没有 `tools/pack/`——读不到就是空白名单，等于把 `<enchanted>` 全判违规。
改成「先读磁盘（开发时改完即生效），读不到退回内嵌副本」。

## P1-8 供应链可审计（v0.5.3）

CI 从无到有。**第一次真跑就抓到 ggpkdoctor 编不过** —— 它引用的
`BundleHygiene.Consolidate` 在 v0.5.0 换成了 `Detach`，那次改动没人回头编这个工具，
它从那以后一直是坏的，而没有任何东西会说。这就是「7 个工程只有一个常编」的代价。

### 依赖锁定：一个静默失败的坑

`Directory.Build.props` 里写 `RestorePackagesWithLockFile=true`，然后
`dotnet restore --force-evaluate`，结果锁文件**一个都没生成**，命令还返回成功。

原因：XML 注释里**不能出现连续两个减号**。我那条注释里写了锁定开关的完整写法，
整份 props 被判「文件无效」，MSBuild 直接跳过导入、不报错、不警告 —— 属性没生效，
于是 `RestorePackagesWithLockFile` 从来没被读到。只有 `dotnet restore -v diag`
里一行「由于文件无效，项目…不由…导入」透出来。

这类失败最贵：命令成功、文件缺失、没有日志。**以后再遇到「属性设了但没效果」，
第一件事是把所有导入的 props/targets 拿去 diag 里看一眼有没有被判无效。**

### ggpkdoctor 按新语义重写

`Detach` 的语义和 `Consolidate` 不同：后者「把重名记录收成一条、文件偏移原样保留」，
前者「旧记录一律停用、换一条时间戳命名的新 bundle 承接本次写入」。重名问题从源头
消失（名字带秒级时间戳，撞不了），代价是旧记录里的文件要重写一遍才落到新 bundle。

修复段因此改成：Detach → **只补写「读不出来」的文件** → `--all` 才整份重铺。
读得出来的一律不动：客户端装的是纯译文、`srcDir` 是全量对照时，硬覆盖等于替玩家
改了选择。这个边界和「别人的内容四选一」是同一个道理。

⚠️ `--fix` 分支**没有真机验证**：手上没有一份「已写坏」的 ggpk。只验了编译和
不带 `--fix` 的体检路径。要验得先造一个坏的。

### 依赖账本

`tools/lib/deps.json` 是唯一事实来源，`tools/lib/DEPS.md` 由 `--doc` 生成。
钉的是「同一个文件名底下是不是同一份东西」：`oo2core.dll` 换版本还叫这个名字，
压出来的 bundle.gz 会不同，但没有任何东西会报错。`--check` 同时校验哈希、字节数、
NuGet 版本与锁文件 resolved 值、以及 DEPS.md 是不是当前投影。

顺手查出两件事：

1. `DatDefinitions.json` 与两份 `schema*.min.json`（共 3.1 MB）**全仓库 0 引用**，
   是 v0.1.0 的研究残留。
2. `LibGGPK3` 是 **AGPL-3.0-or-later**，exe 静态链接了它 → 分发 exe 时整个作品受
   AGPL 约束，而仓库**没有 LICENSE 文件**。`oo2core.dll` 是 RAD/Epic 的 Oodle
   运行时、不可再分发，现在为了「新克隆能一键构建」留在仓库里。两条都要作者拍板，
   写进 DEPS.md 与 README 的「两条待作者拍板的合规问题」。

### 发布可核验，不是可复现

单文件发布做不到位级一致（压缩、打包元数据、PE 时间戳），所以不承诺「重编出同一个
文件」，改为承诺「拿到文件能核对」：`BUILD-INFO.json` + `sbom.cdx.json` +
`MANIFEST.sha256`，三者一起发布。

- `release.py` 先查 `git status --porcelain`，树脏直接拒绝（`--allow-dirty` 才放行）。
  理由：树脏的时候打出来的包，事后没人能说清它是哪个版本。
- SBOM 的 `serialNumber` 用 `uuid5(版本+commit)` 算，不是随机数 —— 同一版本重打发布
  应当逐字节一致，否则每次差异里都会多一行没意义的 UUID。
- 这两个文件必须在 MANIFEST 之前落盘，否则它们自己不会进哈希、也不进 zip。

顺序上有个死结：release 会弄脏树，但 release 要求干净树。解法是先提交代码 +
VERSION + 重建后的 bundle.gz，再在干净树上打快照，最后单独提交 releases/ 并打 tag。
BUILD-INFO 里记的 commit 因此正好是「产物的源码」，不含 releases/ 那次提交。

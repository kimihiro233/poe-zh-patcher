## v0.4.9：旧版补丁器写的对照版，必须认得出并接管

用户一句话点到了根子上：**「旧版补丁器直接认不出不行，应该要能认出来并接管。
准确地说，所有译文和原文的对应版都要能认出来，除非译文和原文对应被破坏了。」**

### 问题

`Detect` 用整块 sha 认状态。v0.4.3 改过 `dual_body` 的排列方式（英文整段附末尾 →
逐组穿插），于是所有早先写过的对照版整块 sha 全变了 → 判「未知」→ 全量替换中止。
这台机器上 25 个文件正好是这个状态，`--set=dualall` 直接 `return 5`，一个字都不写。

### 判据的粒度错了

「内容一样，只是行的排列不同」不该算「不一样」。改判据：从整块降到**行**。

- 行池 = `O` ∪ `T` ∪ `D` ∪ `E` ∪ `Legacy` 所有行，去标记、去首尾空白；
- 每一格的块内行必须全部落在池里，且至少一行来自译文类；
- 全部落得进去 → 我们某版本的排列 → 接管（`Flavor.DualLegacy`），整块换成目标；
- 有一行落不进去 → 那不是我们写的 → 不接管。

这条判据的意义不只是「修好当前这一版」：它不认拼法、只认行，以后 `dual_body`
再改多少次，老客户端都还认得出来。

### 实测

- `--status`：`未知 25` → `旧版对照 25`，每条都报「N 格是原文+译文的排列（0 格仍是原文）」
- `--plan`：25/25 演算通过，0 失败（说明生成字节与 `ShaDualAll` 逐字节一致）
- 真写：47/47 回读通过，状态 `全量对照 42 / 已打补丁 5`，长度仍 `74,730,084,326 B`
- 再跑 `--plan`：需要改动 **0** 个 —— 幂等

### 顺手修的

`--on-modified=skip` 的提示写着「保持它们现在的样子、只翻能对上的」，但实际非 partial
下仍然中止。现在 `skip` 自己就放行（`tolerate = partial || policy == Skip`），
pool 统一按 `!skip.Contains(i)` 排除，不再需要用户猜「是不是还得再叠个 --partial」。

### 新增自检

`--legacy-test`：用数据包三态文本现场拼 11 种情况 —— 6 种排列都要认出（逐组穿插、
英文附末尾带缩进/不带缩进、英文在前、混着来、只有译文），5 种必须认不出（英文那行改一个字、
译文那行改一个字、混进别人的译文、整份都是原文、一格已翻一格未翻要认出）。全部通过。

## v0.5.0：基准 —— 让结果与「改过几次」无关

### 需求怎么一步步收敛的

一开始我提的是「补一份官方原文进数据包」，理由是 statdesc 没有内嵌原文字节，
`--on-modified=ours` 对它做不到。用户的追问把方向改了三遍：

1. 「直接从客户端读，备份在 bundle 中」—— 不要预先打包，运行时读。
2. 「更改前从 content 里读出来并备份」—— 澄清时机：写之前读，那时可能还是原文。
3. 「如果已经被修改的版本，或者被其它补丁修改过呢」—— 指出这个方案的前提（第一次改动之前）
   经常不成立。
4. 「不带，我们优先要保证的是游戏内容的完整性，而不是原文」—— 目标不是保原文。
5. 「在当前基础上做备份，有备份的情况下以备份为前提算，即使多次修改，也可以还原」
   —— 最终方案：**备份即基准，当算式输入**。

最后这条把问题彻底转过来了。之前一直在问「怎么拿到原文」，用户问的是「怎么保证不越打越歪」。
这两个问题的最优解不一样：前者要把 5.9 MB 塞进发布包，后者只要把「第一次见到的样子」当常量。

### 方案

```
基准 = 该文件在这个游戏版本下第一次被本程序看到的完整字节
每次写入 = 基准 + 目标 flavor → 产物
```

输入是常量，结果就是常量。改一次和改两百次算出来的是同一份字节，不存在累积。

关键设计：

- **建基准时尽量取原文**：当前是译文就从数据包还原，还原后 `sha == sha_original` 才作数。
- **只存一次**：已有基准绝不覆盖，否则常量变回变量。
- **按游戏版本分目录**：`client_version + patch_version`。换版本换目录，旧的不删也不读。
- **不参与备份轮转**：备份是后悔药，会轮转；基准是常量，删了算式就变了。
- **sha 对不上就拒绝使用**：宁可从当前重算，也不拿污染的常量去算。

### 真客户端上跑通的五步

```
建基准      47 份全部还原成原文（sha 校验通过才标 Original），52.8 MB
→ --set=translated   47/47 回读通过，产物 sha 与发布产物逐字节一致
→ --set=dualall      47/47 通过
→ --baseline --restore-baseline=statdescriptions
                     42 份整份回到官方原文，状态「官方原文 42 / 已打补丁 5」
→ --set=dualall      47/47 通过，状态精确回到「全量对照 42 / 已打补丁 5」
```

「47 份全部还原成原文」这一步是最有说服力的：从「中文 + 英文对照」精确逆推出官方原文，
逐份 sha 校验通过。说明原文一直在数据包里，只是以前没把它当常量用。

### 顺带修的两件事

1. **`BackupStore.Add` 静默吞异常**。`Program Files` 下没写权限时备份会悄悄失败，然后照样
   写游戏文件 —— 等于把「没退路就不写」破在自己家里。现在 `BackupStore.Create` 和
   `Txn.Begin` 建不出目录就返回 null，上层拒绝写入并说清原因。
2. **`--plan` 与实写不一致**。`inherited`（还挂在旧自建 bundle 上）只在 `!plan` 时算，
   于是演算说「需要改动 0 个」，真跑却写了 47 个。现在两边都算。
3. **JSON 全带 UTF-8 BOM**。`Encoding.UTF8` 在 .NET 里是带 BOM 的，写出来的 `index.json`
   用 Python 直接读会炸。换成 `UTF8Encoding(false)`。

### 单文件 exe 的约束（用户提的）

补丁器是自包含单文件，会被新版本覆盖、会把运行时解到 `%TEMP%`。所以备份**不能跟 exe 走**，
必须跟容器走：`<游戏目录>\.poe-zh\`。现有四类存储（txn / backup / baseline / ggpk）全部
基于 `containerPath`，没有一处用 `AppContext.BaseDirectory`。基准的键是游戏版本而不是
补丁器版本，所以补丁器升级多少次，基准都还是那一份。
